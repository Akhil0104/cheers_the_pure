## Environment and test configuration

- The project uses Django's built-in test runner (`manage.py test`); no `pytest.ini`,
  `pyproject.toml`, or `tox.ini` test configuration exists.
- Dependencies are declared in [`requirements.txt`](../requirements.txt).
- The repository contained stale `env/` and `venv/` launchers that referenced a missing Python
  installation. The active system Python was Python 3.12.10, but initially did not have Django
  installed.
- The declared dependencies were installed into the active Python environment with the command
  documented below. This changed only the local interpreter environment, not repository files.
- `pip check` reported no broken installed requirements after installation.
- Groq and Hindsight were not configured for this baseline. Tests used their existing fallback
  and mocked/error-path coverage; no paid AI API calls were made.

## Warnings and expected unconfigured-service output

The full and targeted test runs emitted the existing django-axes warning:

```text
axes.W003: You do not have 'axes.backends.AxesStandaloneBackend' or a subclass
in your settings.AUTHENTICATION_BACKENDS.
```

This is a configuration warning, not a failing test. It is relevant baseline debt because
[`core/settings.py`](../core/settings.py) conditionally inserts the older
`axes.backends.AxesBackend` name outside test runs, while the installed django-axes release
recommends `AxesStandaloneBackend`.

The tests also logged expected safe failure/fallback messages for unconfigured Groq and
Hindsight. These included:

- Groq unavailable/unconfigured fallback paths
- Hindsight authentication, malformed-response, and timeout handling tests
- SaaSsum generation unavailable when Groq is not configured

No raw environment-variable values were printed. One test log displayed a masked Hindsight key
fragment generated by existing logging; no credential value was exposed.

## Existing failures

No test failures were observed after restoring the declared dependencies. The only pre-existing
baseline issue observed at runtime is the django-axes `W003` warning described above.

The initial inability to run Django commands was an environment/dependency issue, not an
application test failure. It was resolved locally by installing [`requirements.txt`](../requirements.txt)
into the active Python 3.12 interpreter. The stale `env/` and `venv/` launchers remain
unchanged and should not be used until recreated.

## What this baseline does not verify

- Live Groq generation or paid AI usage
- Live Hindsight service availability or production memory persistence
- Real Stripe checkout, webhook delivery, or payment settlement
- SMTP/SMS delivery
- Browser rendering or manual SaaSsum workspace behavior
- Production database/cache/deployment configuration

These require explicit staging credentials and should be tested separately without using
production customer or payment data.

## Reproduction steps

1. Use a supported Python 3.12+ interpreter.
2. From the repository root, install dependencies:

   ```powershell
   python -m pip install -r requirements.txt
   ```

3. Confirm package consistency:

   ```powershell
   python -m pip check
   ```

4. Run system and migration checks:

   ```powershell
   python manage.py check
   python manage.py migrate --plan
   ```

5. Run the focused or complete suite:

   ```powershell
   python manage.py test ai_builder app dispatch --verbosity 1
   python manage.py test --verbosity 1
   ```

Do not use `migrate` without `--plan` during this baseline unless applying migrations is
explicitly approved for the target environment. Do not print `.env`, dump the database, or
invoke real payment/AI services.
